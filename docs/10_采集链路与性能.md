# 10 · 采集链路与性能

> 本文描述**一个视角从"转台停下"到"图像落盘"**的完整链路：设计约束、
> 实现取舍与实测数据。架构总览见 `09_架构说明（重构后）.md`，
> 相机/电机选型见 `02_硬件选型与参数.md`。

| 环节 | 模块 |
|---|---|
| 相机打开、格式协商、通道判定、取帧 | `software/triniscan/hardware/camera.py` |
| 转台驱动、角度计划 | `software/triniscan/hardware/turntable.py` |
| 后台写图 | `software/triniscan/common/async_writer.py` |
| 编排 | `software/triniscan/core/pipeline.py::ScanPipeline.acquire` |

---

## 1. 一帧是怎么来的

### 1.1 调用链

```
ScanPipeline.acquire()                        core/pipeline.py
 ├─ resolve_scan_plan(cfg)                    整数步角度计划
 ├─ Camera.open()                             格式协商 → 参数锁定 → 通道判定
 ├─ Turntable.open() / .home()                归零
 └─ for i in range(n):
      ├─ Turntable.rotate_steps(k)            阻塞至固件 busy=0，再补 settle_ms
      ├─ Camera.grab()                        丢弃 discard_frames 帧后返回一帧
      └─ AsyncImageWriter.submit(path, img)   入队即返回（~0.1 ms）
 └─ AsyncImageWriter.close()                  离开 with：排空队列，最后几张也落盘
```

### 1.2 每视角时序

```
┌──────────────┬───────────┬──────────────┬──────────────┐
│ 转台转动      │ 停稳延时   │ 相机取帧      │ submit 入队   │  采集线程（串行）
│ rotate_steps │ settle_ms │ grab()       │              │
│   ~41 ms     │   30 ms   │   ~15 ms     │   ~0.1 ms    │
└──────────────┴───────────┴──────────────┴──────────────┘
                                              │
                                              └──► 后台线程：PNG 编码 + 写盘（~55 ms）
                                                    与下一个视角并行，不阻塞采集
```

关键点：**写盘与采集并行**。写图既不需要相机也不需要转台，把它留在
采集线程里等于让两者白等。

## 2. 像素格式：本链路最大的性能开关

### 2.1 为什么 YUY2 只有 10 fps

1280×800 = 1 024 000 像素。USB 2.0 高速理论 480 Mbit/s（60 MB/s），
UVC 等时传输扣除包开销与驱动后，实测可用约 **36–40 MB/s**。

| 格式 | 每像素 | 帧大小 | 60 fps 需求 | 结果 |
|---|---|---|---|---|
| YUY2（未压缩 4:2:2） | 16 bit | **2.05 MB** | **122.9 MB/s** | 超带宽 → 约 10 fps |
| MJPG（帧内压缩） | ≈1.5 bit（估） | **≈0.19 MB** | **≈11.5 MB/s** | 带宽不再是瓶颈 |

> MJPG 的 1.5 bit/px 是平均压缩比的量级估计，随画面纹理变化；激光
> 扫描画面大面积暗背景，实际压缩率更高。推导见 `02` §2.6。

### 2.2 设置顺序陷阱

部分 UVC 驱动（实测 `CAP_DSHOW` + Sunplus 方案）在**改变分辨率时会
重置像素格式**：

```python
cap.set(cv2.CAP_PROP_FOURCC, MJPG)        # 成功
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 1280)   # 驱动重置格式 → 退回 YUY2
```

日志写着 "fourcc=MJPG"，实际跑 10 fps，且**没有任何报错**。

因此 `Camera._apply_format()` 的步骤是固定的：

```
1. 分辨率 + 帧率
2. 四码（含回读验证）
3. 若四码设置改变了分辨率 → 重设一次分辨率，再次确认四码
4. CAP_PROP_BUFFERSIZE = 1（限制驱动内部缓冲，降低延迟）
```

这不是编码风格问题，是驱动行为决定了它必须是这个顺序。

### 2.3 回读验证，而不是假定成功

`_try_fourccs()` 依次尝试候选四码，每次**回读**实际生效值：

```python
cap.set(CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*cc))
got = _fourcc_to_str(int(cap.get(CAP_PROP_FOURCC)))
if got.upper() == cc.upper():   return cc     # 已生效
if not got:                     return cc     # 后端不回读，只能采信请求值
# 否则尝试下一个候选
```

全部失败时记录 warning："将使用驱动默认格式，高分辨率下帧率可能受
USB 带宽严重限制"。**不把请求值当成功值回报**——否则排查时日志本身
就在误导你。

## 3. 灰度判定：三通道不等于彩色

### 3.1 问题

UVC 没有"纯灰度"像素格式。黑白相机被包装成 `YUY2` / `MJPG` 后，
OpenCV 解码一律给出 **BGR 三通道**。只用 `frame.ndim == 2` 判定，
会把黑白相机误报成彩色，日志与通道选择都会走错方向。

### 3.2 两级判据（`Camera._probe_channels`）

| 级别 | 条件 | 结论 |
|---|---|---|
| 1 | `frame.ndim == 2` | 单通道，黑白（最优路径） |
| 2 | `median(\|R−B\|) ≤ 3` 且 `median(\|R−G\|) ≤ 3` | 三通道但无色差 → 黑白 |

用**中位数**而非均值：少量彩色像素（激光本身、反光）不会拉偏判据。

### 3.3 阈值 3 的由来

灰度值 y 写入 Y、U = V = 128 时，YUV→BGR 的整数换算给出
`R = y + 1.402(V−128) = y`、`B = y`，量化误差不超过 **2 个灰度级**。
实测本机相机 `B == R` 的像素占 100%、`R−G ∈ {1, 2}`。阈值取 3 留 1
级余量；正常彩色场景的通道差远大于此。

### 3.4 配置不一致只告警

`camera.mono: true`（配合 `extraction.channel: gray`）与实测不符时只记
warning、不中断。现场常有"标称黑白、驱动仍给彩色"的混用情况。

## 4. 异步落盘

### 4.1 为什么单独成模块

落盘是纯 CPU/磁盘 I/O，与"如何取图"无关。标定、离线重处理同样需要
"批量存图但不阻塞主循环"。`common/async_writer.py` 不依赖相机，
可以脱离硬件单测。

### 4.2 四条设计约束

| 约束 | 实现 | 不做会怎样 |
|---|---|---|
| **失败可见** | 后台线程捕获异常，`close()` 聚合成 `ImageWriteError` 抛出 | 图没写成，扫描却宣告成功 |
| **有界队列** | 默认 30 张，满则 `submit()` 阻塞（背压） | 慢磁盘时内存随视角数线性增长 |
| **关闭排空** | `close()` 先等队列清空再 join | 最后几张图未落盘，调用方已认为完成 |
| **线程安全** | 单生产者 + `Condition` 保护队列与计数 | 竞态丢帧、计数错乱 |

### 4.3 背压的实际含义

采集端每视角约 76 ms，写端每张约 55 ms，**写快于采**，队列不会
持续积压；30 的深度是安全裕量：

- 磁盘正常 → 不触发背压，采集不受影响；
- 磁盘变慢（网络盘、机械盘、杀毒实时扫描）→ 队列积满后 `submit()`
  阻塞，采集被拖慢。**这是有意为之**：宁可整体变慢，也不在内存里
  堆积数百张图。

### 4.4 使用方式

```python
with AsyncImageWriter(queue_size=30) as writer:
    for i in range(n):
        image = cam.grab()
        writer.submit(path, image)      # 立即返回
# 离开 with：队列排空，此后可保证所有图片已写盘
```

队列深度由 `pipeline._writer_queue_size()` 读取，配置键
`output.writer_queue`，**默认 30**。该键未在 `default.yaml` 中列出；
需要调整时手动添加（`all_fields()` 只枚举 yaml 中已有的键，因此它
不会出现在界面参数表里）。

### 4.5 与 `grab_and_save()` 的分工

`Camera.grab_and_save()` 保留给**单张、需要立即确认落盘**的场景
（标定、调试）。`acquire()` 使用 `grab()` + `submit()`。

## 5. 实测数据

测量条件：Windows 10；相机 1280×800、`CAP_DSHOW`、`fourcc=MJPG`、
`discard_frames=1`；写盘测试用真实激光扫描帧（非随机噪声，保证 PNG
压缩耗时真实）；本机 SSD。**换机器、换磁盘会有差异，这里的值用于
判断量级与瓶颈位置。**

### 5.1 单项耗时

| 操作 | 改前 | 改后 | 说明 |
|---|---|---|---|
| `grab()` | ~100 ms | **~15 ms** | 3 帧 × ~33 ms（YUY2 10 fps）→ 1 帧 × 14.5 ms（MJPG 69 fps） |
| PNG 写盘 | 55.7 ms（占采集线程） | **0.1 ms**（入队） | 后台线程实际 55.2 ms/张 |
| 写盘完成时刻 | 本视角内 | 下一视角期间 | 与采集并行 |

### 5.2 每视角与整次扫描

| 项目 | 改前 | 改后 |
|---|---|---|
| 转台转动（46 微步） | ~41 ms | ~41 ms |
| 停稳延时 `settle_ms` | 30 ms | 30 ms |
| 取帧 | ~100 ms | ~15 ms |
| 写盘（占采集线程） | 56 ms | 0 ms |
| **每视角合计** | **~460 ms** | **~76 ms** |
| **720 视角采集** | **~330 s** | **~55 s** |

异步模块单独压测（20 张真实帧）：`submit` 合计 2.3 ms（0.115 ms/张），
`close()` 排空 1105 ms（20/20 落盘，55.2 ms/张）。

> 上表只含采集阶段。标定加载、重建与体积计算另计；运行时日志会给出
> `采集完成: N 视角，用时 X s（Y ms/张）`。

### 5.3 剩余的 76 ms 花在哪

```
转台转动   41 ms  ← 受 step_us 与 microstep 限制（硬件）
停稳延时   30 ms  ← 覆盖相机流水线残留帧（可调，见 6.2）
取帧       15 ms  ← 与停稳部分重叠，实际未额外累加
```

要再压缩只有两条路：降 `settle_ms`（会拍进运动模糊）或降
`turntable.step_us`（受电机扭矩与失步风险约束）。二者都是硬件约束，
不是软件优化空间。

## 6. 已知限制

### 6.1 `views` 持有全部原始帧

`acquire()` 返回的每个视角都带 `"raw": ndarray`，`reconstruct_views()`
直接消费它。因此：

```
720 视角 × 1280 × 800 × 3 B ≈ 2.1 GB 常驻内存
```

这是"先采集、后重建"分离设计的必然结果——重建阶段不再依赖相机，
也允许对已采集结果反复调参重算。**异步写盘不降低这部分内存**，
它只把 I/O 从每视角关键路径上移开。

部署前按 `视角数 × 3 MB` 估算内存；若需降低，可改为采集后从磁盘
按需读取（代价是重算时多一次磁盘往返）。

### 6.2 `settle_ms` 的语义变了

旧代码每张图在相机里要等 100 ms 以上（YUY2 低帧率），`settle_ms` 的
作用被掩盖。改后每视角只有 ~15 ms 取帧，`settle_ms` 真正承担
"覆盖相机流水线残留帧"的职责：

```
需要覆盖的帧数 ≈ ceil(settle_ms / 帧周期) = ceil(30 / 14.5) ≈ 2 帧
```

若结果出现**重影或边缘发散**，先试 `turntable.settle_ms = 45`
（3 帧余量），代价是 720 视角约 +11 s。

### 6.3 相机索引会漂移

`camera.index` 由操作系统枚举顺序决定。笔记本内置摄像头与外接相机
同时存在时，谁先枚举谁占 0。换 USB 口、换插拔顺序后可能失效，表现为
"打开相机失败"。

排查：`设备管理器 → 摄像头` 确认设备存在；依次尝试 `index` 0–3，用
实际分辨率区分（本机外接相机 1280×800，内置摄像头 1280×720）。

## 7. 排查手册

| 症状 | 先查 | 常见原因 |
|---|---|---|
| 帧率只有 ~10 fps | 日志中四码是否生效 | 四码没设上，退回 YUY2（§2.2） |
| 日志说"彩色"但画面是灰度 | `camera.mono` 与实测 | §3.2 判据会正确识别并给出提示 |
| 打开相机失败 | `camera.index` | 索引漂移（§6.3） |
| 扫描中途越来越慢 | 磁盘占用、杀毒实时扫描 | 写盘跟不上，触发背压（§4.3） |
| 点云重影 / 边缘发散 | `turntable.settle_ms` | 残留帧未丢净（§6.2） |
| 采集中断且报 `ImageWriteError` | 磁盘空间、路径权限 | 写盘失败被聚合上报，非静默 |

## 8. 改动这一层的约束

1. **不要调整 `_apply_format()` 的步骤顺序**——由驱动行为决定。
2. **不要移除四码回读**——它是"假成功"的唯一防线。
3. **不要改成无界队列**——内存会随视角数线性增长。
4. **`submit()` 之后不要原地修改图像数组**——不复制，后台线程拿到的是
   引用。采集循环每帧都是新数组，天然满足；若将来复用缓冲区，必须先
   复制。
5. **采集日志用 `log.debug` 并聚合进度**——720 视角 × 每视角多条会淹没
   界面日志面板。现有实现每 10 张打一条。
